# T19.2: VCS Provider Abstraction Refactoring — Migration Guide

**Status:** Implementation Complete  
**Date:** 2026-08-06  
**Changes:** Modular architecture, MCP-ready, fail-closed design

---

## What Changed

**Before (T19):**
- Single monolithic file: `scripts/lib/vcs-provider-interface.cjs`
- All providers in one file (~350 lines)
- Procedural provider instantiation

**After (T19.2):**
- Modular structure under `scripts/vcs/`
- One provider per file + factory
- `vcs/resolve.cjs` handles config loading with fail-closed design
- Bitbucket Cloud ready for MCP integration

---

## New File Structure

```
scripts/vcs/
├── provider.cjs              # VCSProvider base class
├── index.cjs                 # Factory: createVCSProvider()
├── resolve.cjs               # Config loader + provider resolver (fail-closed)
└── providers/
    ├── github.cjs            # GitHub Cloud/Enterprise
    ├── bitbucket-cloud.cjs   # Bitbucket Cloud (MCP-first, curl fallback)
    └── bitbucket-server.cjs  # Stub (not implemented yet)
```

## For End Users (Using Keel)

### No Breaking Changes

If you already have `.keel/vcs.yml`, **nothing changes for you**:
- Continue using `/keel:approve-phase <story> <phase> --via-pr <PR#>` exactly as before
- Config format unchanged
- Token file location unchanged

### New Setup Workflow (Recommended)

For fresh projects or to re-initialize:

```bash
# 1. Initialize VCS configuration
keel setup-vcs

# Follow the proposal, then confirm:
keel setup-vcs --confirm --provider github --owner myorg --repo myapp

# 2. Create auth token file
mkdir -p ~/.keel/secrets
echo "YOUR_GITHUB_TOKEN" > ~/.keel/secrets/github.token
chmod 600 ~/.keel/secrets/github.token

# 3. Verify approval gate
keel approve-phase STORY-001 3 --via-pr 123
```

## Architecture Improvements

### 1. Modular Design
- Easy to add new providers (GitLab, Azure, etc.)
- Each provider fully encapsulated
- Clean inheritance hierarchy via VCSProvider base class

### 2. MCP Integration Ready
- Bitbucket Cloud has MCP-first path (will use Atlassian Rovo when available)
- Graceful fallback to curl if MCP unavailable
- No code changes needed when MCP tools become available

### 3. Fail-Closed Design
- `vcs/resolve.cjs` halts immediately if `.keel/vcs.yml` missing or malformed
- Never silently defaults to any repo
- Clear diagnostic messages guide users to fix config

### 4. Connection Testing
- `keel setup-vcs` now tests connection before writing config
- Catches auth token issues at setup time, not at approval time
- Reduces support burden for "connection failed" issues

## API Reference

### VCSProvider Interface

All providers implement:

```javascript
class VCSProvider {
  async findPullRequest(branchName, storyId)    // → {number, state, branch}
  async getPullRequestStatus(prRef)             // → {state, approvals, mergeable, branch}
  async postComment(prRef, text)                // → void
  async testConnection()                        // → {ok, message}
  resolveRepoContext()                          // → {provider, owner, repo, base_url}
}
```

### Resolver API

```javascript
const { resolveVcsProvider, vcsConfigExists, VCS_CONFIG_PATH } = require('./vcs/resolve.cjs');

// Load + validate config, instantiate provider (fail-closed)
const provider = resolveVcsProvider();

// Check if config exists (for setup workflows)
const exists = vcsConfigExists();
```

## Troubleshooting

### Connection Test Fails on Setup

**Error:** `Bitbucket Cloud connection failed: Unauthorized`

**Fix:** Ensure auth token file exists and is valid:
```bash
cat ~/.keel/secrets/bitbucket.token
# Should contain your Bitbucket app password
```

### PR Approval Gate Rejects Valid PR

**Error:** `VCS approval failed: PR branch "feat/other" does not match story ID "STORY-001"`

**Reason:** PR branch must contain the story ID (T20 branch matching).

**Fix:** Ensure PR head branch is related to the story:
- ✅ `feat/STORY-001-my-feature` (contains STORY-001)
- ✅ `fix/STORY-001` (contains STORY-001)
- ❌ `chore/other` (doesn't match STORY-001)
